# Agent Job Workers: Explanation

## Overview

| Approach | Role | Time | Space | Use when |
|----------|------|------|-------|----------|
| lazy-leases | optimal | O(j) per claim for j jobs, O(s) per progress for s saved steps, O(a) per call for a attempts, O(1) otherwise | O(j + s) for j jobs and s saved steps | default answer; one record per job, a counter for the backlog, and buckets and breakers that are brought up to date only when they are looked at |

Here `j` is the number of jobs submitted, `s` the number of steps saved (for `progress`, those of one job), and `a` the attempts of one call, at most `maxAttempts`.

## How the design grows level by level

| Level | Change | What the design adds |
|-------|--------|----------------------|
| 1 | A queue with leases and idempotent submits | A map from job id to a record (holder, end of lease, done), in submission order, and one helper that says whether a lease is active at `now` |
| 2 | Progress in the shared store | A list of outputs in the job's record, a checkpoint that checks the lease first and appends only the next step |
| 3 | A worker count from the backlog | A counter of done jobs, a rounded-up division held between bounds, and the time of the last change, empty until the first one |
| 4 | Limits, retries and breakers for the tools | A token bucket per tool and per tenant, a breaker per tool, and a call written as a loop over attempts with its own time |

The idea that carries the whole problem is that **nothing happens between calls**. No timer ends a lease, refills a bucket or moves a breaker to half-open. Each of them stores the moment that matters (when the lease ends, when the bucket was last looked at, when the breaker opened) and derives its state from `now` when someone asks. That is what makes the system deterministic and testable, and it needs no timer per object.

## Approach: lazy-leases (Lazy leases, a step log per job, a backlog rule, and buckets and breakers updated on demand)

### Intuition

Each layer protects against one failure. A **lease** protects against a worker that dies: the job is the worker's only for a while, so a dead worker loses it by doing nothing. A **job id** protects against a client that sends twice. **Checkpoints in the job's record** protect against losing work: the worker is stateless, so any worker can continue. The **backlog** is the right input for the controller because agent workers wait on models and tools instead of computing. **Buckets, retries and breakers** protect the tools from the crowd that the controller creates. Each of them is a few fields and a comparison; the work is in stating each comparison exactly (`<` or `<=`, before or after a step, from the last change or the last look) and in asking the checks in the right order.

### Algorithm

1. Keep a map from job id to a record: the worker the lease was last given to, the second the lease ends, whether the job is done, and the list of saved outputs. Insertion order is submission order. A lease is **active** at `now` when the record has a holder, is not done, and `now < end`. A worker **holds** a job when it is the job's holder and the lease is active.
2. `submit`: `"duplicate"` if the id is in the map, whatever its state; otherwise add a record and return `"queued"`.
3. `claim`: walk the map in order. If a job is held by this worker, return it and change nothing. Remember the first job that is not done and has no active lease. After the walk, give that job to the worker with an end of `now + leaseSeconds`, or return `""`.
4. `heartbeat`: if the worker holds the job, set its end to `now + leaseSeconds`; otherwise `"lost"`. `complete`: first `"already_done"` for a done job, then `"lost"` unless the worker holds it, then mark it done, clear its holder and count it. `jobState` reads the record the same way.
5. `checkpoint`: `"lost"` unless the worker holds the job; `"duplicate"` when `step <= len(outputs)`; `"gap"` when `step > len(outputs) + 1`; otherwise append the output and renew the lease from `now`. `progress` copies the list.
6. `scale`: the backlog is the number of jobs minus the number done. `needed = ceil(backlog / jobsPerWorker)`, `desired = min(max(needed, minWorkers), maxWorkers)`. Equal to the count: `"hold"`. Otherwise pick `upCooldown` or `downCooldown` by direction; when no change is on record or `now - lastChange >= cooldown`, set the count to `desired` and `lastChange` to `now`, else `"cooldown"`. The alert compares the backlog with `alertBacklog`.
7. A bucket stores its tokens and the time it was last looked at. To ask it for a token at `t`, add `refillPerSecond * (t - last)`, cut to `capacity`, set `last = t`, and compare the tokens with 1. A breaker stores its count of failures in a row and the time it opened, empty while closed; its state at `t` is closed when that time is empty, open while `t < opened + openSeconds`, and half-open after.
8. `call`: set `t = now`. Loop: if the breaker is open at `t`, return `circuit_open`; if the tenant's bucket, then the tool's, has no token at `t`, return its reason; all of these before any token is taken. Take one token from each bucket, read the next outcome and tell the breaker (a success clears the count and closes it; a failure reopens a half-open breaker at `t`, and otherwise adds one and opens it at the threshold). Return `ok` on a success and `retries_exhausted` after `maxAttempts` attempts; otherwise add `min(baseDelay * 2^(k - 1), maxDelay)` to `t` after the `k`-th failure and loop.

### Correctness

Every state the statement defines is a function of stored fields and `now`, and each method computes it from the same helper, so two methods can never disagree about whether a lease is active or a breaker open. A lease that is not renewed is active exactly for the seconds `t` to `t + leaseSeconds - 1`, because `active` is `now < end`. A worker holds at most one job: `claim` returns the job it holds before it looks for a free one, and only `claim` creates a lease. The free job a claim takes is the first in submission order among the jobs that are neither done nor actively leased, because the map is walked in insertion order and a job's place never changes. `complete` asks `done` before ownership, so a done job always answers `already_done`, and a job is counted done once. A checkpoint appends only when `step` equals the number of saved steps plus one, so the list always holds steps `1..n` with no gap, and every saved output was written by a worker that held the job at that moment; progress lives in the job's record, so a new lease or a new worker sees all of it.

The backlog counter equals the jobs submitted minus the jobs completed, since `complete` is the only way to finish a job and it counts each one once. The rule of level 3 is evaluated literally, and the last change is recorded only when the count changes, so a cooldown is measured from the last change and never from an evaluation that held. For buckets, bringing a bucket up to date at an earlier time and then at a later one gives the same tokens as bringing it up to date at the later time only: if the cap was not reached in between, the gains add up; if it was, both give `capacity`. So looking at a bucket during a refused attempt changes nothing that a later attempt can see. A refused attempt takes tokens only after every check passed, so it takes none. A call's time only grows, and the constraints keep every later `now` at or after its end, so no bucket or breaker ever sees time go back.

### Complexity

- Time: O(j) per claim for j jobs, O(s) per progress for s saved steps, O(a) per call for a attempts, O(1) otherwise — a claim walks the map once; heartbeat, complete, jobState and checkpoint look up one record (a checkpoint also stores its output); `scale` reads two counters; each attempt of a call does a constant number of bucket and breaker operations, and `a` is at most 10.
- Space: O(j + s) for j jobs and s saved steps — one record per job, one string per saved step, plus one bucket per configured tool or tenant and one breaker per configured tool.

### Trade-offs

- **The walk in `claim`.** A walk over all jobs is the simplest correct claim, and it is slow with many jobs. A queue of free jobs ordered by submission number, a heap of leases ordered by end and a map from worker to the job it holds would make a claim logarithmic: expired leases move from the heap back into the free queue when a claim looks. The order "submitted first" makes that queue a priority queue on the submission number, not a plain FIFO, because a job whose lease ended returns to its old place.
- **Lease length.** A short lease hands a dead worker's job to another worker quickly but forces frequent heartbeats, and a worker that pauses longer than the lease (a long tool call, a slow machine) loses a job it is still running. The checkpoint that renews the lease ties the lease to real progress. Gray and Cheriton make the same trade for file caches: with leases, failures affect performance rather than correctness, and short leases keep that effect small.
- **What a lease cannot do.** The lease check in `checkpoint` protects the shared store, because the store checks it. A worker that pauses past its lease and then writes somewhere else is not stopped, which is the case for a fencing token, a number that grows with every claim and that the other system checks (Kleppmann). Duplicated side effects of a step that ran but was not saved are also still possible, so the steps themselves should be idempotent where they can.
- **The controller.** A backlog divided by a target per worker is the simplest rule, and it does not look at how long a job takes. By Little's law, the average number of jobs in the system equals their arrival rate times the average time each spends there, so a steady backlog alone does not tell how fast jobs flow: the same 100 jobs keep 10 workers busy for 10 minutes if each takes a minute, and for 10 hours if each takes an hour. A controller could also watch the age of the oldest waiting job, which grows when jobs take longer even while the backlog stays the same. Cooldowns are the usual damping of threshold rules (Lorido-Botrán and colleagues); a stabilization window (the highest desired count over a period) reacts to the trend instead of to one sample.
- **The gateway.** Retries help with brief failures and hurt during a long outage, since every retry is one more call to a tool that is down. The breaker is what bounds that: once open, it refuses at once, without spending tokens or worker time. Retries here are deterministic. Workers that fail together and back off by the same rule also retry together; adding a random spread to each wait separates them, and needs a seeded source to stay testable.
- **Check order.** The breaker comes first because a call to a tool that is down should not cost the tenant anything, and the tenant comes before the tool so that the reason names the limit the caller can do something about. Any fixed order works as long as a refused attempt takes nothing.

### Pitfalls and edge cases

- Level 1: a lease is over at its end second (`now < end`, not `<=`). A heartbeat after the end is `lost` even when nobody else has claimed the job, and it renews from `now`, not from the old end. A worker's second `claim` returns the job it holds and does not renew it. A job whose lease ended keeps its place ahead of newer jobs. A done job's id stays a duplicate forever, and a late completion of a done job hears `already_done`, not `lost`. Completing a job must release the worker, or its next `claim` returns the done job.
- Level 2: check the lease before anything else, so that a worker whose lease is over hears `lost` even for a step that is saved. Keep the first output of a step on a duplicate. Neither a duplicate nor a gap renews the lease; only a saved step does. Progress must not be cleared by a new claim or kept per worker.
- Level 3: the backlog counts the jobs being worked on, not only the waiting ones, and not the done ones. Round up. With `minWorkers` 0 an empty backlog scales to zero, and with a minimum above 0 the controller never goes below it. The first change does not wait, so the last change starts as "none", not 0. A cooldown counts from the last change in either direction, and a `hold` or a `cooldown` does not restart it. The alert compares the backlog with `>=`.
- Level 4: a bucket starts full and is capped after each refill. Count the refill from the last look, not from the last token taken. Every attempt, retries included, takes a token from each bucket, and a refused attempt takes none, even from the buckets that would have allowed it. The wait after the first failure is `baseDelay`, not twice it, and it is capped. Failures count in a row: a success clears them. The breaker opens when the count reaches the threshold, is half-open at exactly `opened + openSeconds`, and a failed trial reopens it for a whole new period while a successful one clears the count. A refused retry ends the call with its own reason and time, and `attempts` counts only the attempts made.

### Language notes

- Python: a `dict` keeps insertion order, so it is both the job index and the queue. Small `@dataclass(slots=True)` records keep each layer's fields in one place, and `-(-a // b)` rounds an integer division up without floating point. `None` marks "no change on record" and "breaker closed".
- TypeScript: a `Map` iterates in insertion order too. `Math.ceil(backlog / per)` is exact for these sizes, since both are small integers. Classes with plain fields keep the bucket and the breaker; the runner strips types without compiling, so constructor parameter properties (`constructor(private x: number)`) are not allowed, and the fields are assigned in the constructor body instead. `null` marks the empty times.

## Further reading

- C. G. Gray and D. R. Cheriton, "Leases: An Efficient Fault-Tolerant Mechanism for Distributed File Cache Consistency", Proceedings of the 12th ACM Symposium on Operating System Principles (SOSP 1989), 202–210, [doi:10.1145/74850.74870](https://doi.org/10.1145/74850.74870): a lease as "a contract that gives its holder specified rights over property for a limited period of time", and the finding that with leases, non-Byzantine failures affect performance rather than correctness, an effect that short leases keep small.
- M. Kleppmann, ["How to do distributed locking"](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html), 2016: a lock holder that pauses past its lease and then writes, and fencing tokens, numbers that grow with every acquisition, with which the storage refuses a write older than one it has already seen.
- [RFC 9110, HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110), section 9.2.2, "Idempotent Methods": a request method is idempotent when the intended effect of several identical requests is that of one, which lets a client repeat such a request automatically when a communication failure occurs before it can read the response.
- T. Lorido-Botrán, J. Miguel-Alonso and J. A. Lozano, "Auto-scaling Techniques for Elastic Applications in Cloud Environments", technical report EHU-KAT-IK-09-12, University of the Basque Country, 2012, section 5.1, "Static Threshold-based Rules": rules for scaling up and for scaling down, each followed by an inertia period of its own, a minimum and a maximum number of machines, and the advice to set "an inertia, cooldown or calm period" in which no scaling decision is made, to avoid oscillations. A later version is "A Review of Auto-scaling Techniques for Elastic Applications in Cloud Environments", Journal of Grid Computing 12(4), 559–592, 2014, [doi:10.1007/s10723-014-9314-7](https://doi.org/10.1007/s10723-014-9314-7).
- J. D. C. Little, "A Proof for the Queuing Formula: L = λW", Operations Research 9(3), 383–387, 1961, [doi:10.1287/opre.9.3.383](https://doi.org/10.1287/opre.9.3.383): the mean number of units in a system equals the arrival rate times the mean time a unit spends in it.
- [RFC 2697, A Single Rate Three Color Marker](https://www.rfc-editor.org/rfc/rfc2697), 1999: token buckets that start full, gain tokens at a fixed rate up to their size, and accept a packet as within the rate only when a bucket holds at least as many tokens as the packet has bytes, which are then taken.
- [RFC 6298, Computing TCP's Retransmission Timer](https://www.rfc-editor.org/rfc/rfc6298), 2011: on a timeout the timer is doubled ("back off the timer", rule 5.5), and a maximum may be placed on it (rule 2.5), the capped exponential backoff of level 4.
- M. Fowler, ["CircuitBreaker"](https://martinfowler.com/bliki/CircuitBreaker.html), 2014: closed, open and half-open states, a breaker that trips when failures reach a threshold, and a trial call after a timeout that "will either reset the breaker if successful or restart the timeout if not"; it credits Michael Nygard's book *Release It!* with popularizing the pattern.
