# Exercise: Review: Payment Retry

## Prompt

```markdown
# Review: Payment Retry

## Context

The checkout service (Java 21, Spring Boot) charges shoppers' cards through a payment service provider (PSP). `PspClient` wraps the PSP's REST API. Last month the PSP had a 20-minute partial outage (slow responses, timeouts and some 503s) and checkout failed for many shoppers; one action item from the incident review was "add retries to the PSP client". This pull request implements it.

Facts about the codebase and the PSP that are not visible in the diff:

- `POST /v1/charges` and `POST /v1/refunds` answer `201 Created` when they create a charge or refund, `402` for a declined card (with a decline code), `400` for an invalid request, `401` for a bad API key, `429` with `Retry-After` when rate limited, and occasionally `5xx`.
- The PSP supports an `Idempotency-Key` header: a repeated key within 24 hours replays the original response instead of creating a second charge.
- `ChargeRequest` carries `paymentId`, the id of the payment row the checkout service creates before charging.
- `CheckoutService.placeOrder` catches `PspException`: declines are shown to the shopper with the decline reason; other failures are retried up to 3 times.
- Requests run on a Tomcat pool of 200 threads per instance. The load balancer times out after 30 seconds, and the mobile apps retry a checkout that timed out.

## Pull request

**Retry PSP calls on failure**

> Incident follow-up: transient PSP failures should not fail checkout, so every PSP call now retries with linear backoff until it succeeds. Also switches the HTTP client to HTTP/2. Added a unit test that fails twice and then succeeds.

## Task

Review the change as you would a teammate's pull request, in about 40 minutes. For each issue, give its location, its severity (blocker, major, minor or nit), what goes wrong (in production terms: money, threads, shoppers) and the change you would ask for. Ask about intent where the right fix depends on it. End with your overall verdict.
```

## Rubric

### Finding the issues

C1. Notices that only 200 counts as success while the PSP answers 201, so successful charges are repeated.
C2. Flags retried POSTs without an idempotency key as a double-charge risk on ambiguous failures.
C3. Flags the unbounded loop and connects it to thread-pool exhaustion and a full checkout outage.
C4. Flags that permanent failures (declines, 400, 401) are retried.
C5. Flags the missing connect and request timeouts, and that a stalled call never reaches the retry logic.
C6. Flags `catch (Exception)` swallowing the cause and retrying decode or programming errors.
C7. Flags the swallowed interrupt and notes the old code handled it correctly.
C8. Notices that `PspException` can no longer be thrown, breaking decline handling in the caller.
C9. Flags retry amplification with the existing retries in `CheckoutService`.
C10. Flags linear backoff without jitter and the test that mocks the wrong status code and sleeps for real.

### Prioritization

C11. Leads with the money-losing and outage-causing issues, before logging and style.
C12. Distinguishes what the change introduced from what it made worse (timeouts were already missing, but retries make them critical).
C13. Gives an overall verdict with a short reason.

### Actionable comments

C14. Proposes a concrete retry policy: attempt limit, deadline, retryable conditions, backoff with jitter, `Retry-After`.
C15. Derives the idempotency key from the payment, the same across attempts and checkout retries.
C16. Suggests keeping the old `send` as the inner call and wrapping it, or using an existing resilience library.
C17. Lists the missing tests (201, 402, retry limit, idempotency header, timeout, interruption) and asks for injectable delays.

### Tone and collaboration

C18. Acknowledges the incident action item and the intent of the change.
C19. Explains failures as scenarios (what the shopper and the PSP see), not as rule violations.
C20. Suggests splitting the unrelated HTTP/2 change without making it a blocker.

### Asking about intent

C21. Asks for the checkout latency budget to size the deadline.
C22. Asks which layer should own retries.
C23. Asks whether refunds should be retried synchronously or queued for asynchronous retry.
