# Review: the facts of the testing guides

The seven guides of the path "Testing: from your first assertion to mutation and contract tests" ([guides](../specs/guides.md), [ADR 0025](../decisions/0025-concept-guides-and-learning-paths.md)) state facts about papers, the xUnit test patterns, essays and articles on testing, and Python's standard library. This page lists each one with where it was checked, so that the independent review starts from the sources.

"Quote" means the exact text was read at that source: on the web page, or in the text extracted from the PDF with `pdftotext` (from PostScript through `ps2pdf` first, for one paper). "Run" means an example of the guide, or a one-off program, printed it, on CPython 3.13.12. "Arithmetic" means the number was computed from the stated inputs. Bibliographic data (authors, venue, volume, pages, year) of every paper was checked against its Crossref record. A fact that could not be checked is not in the guides; the last sections list those, the citation choices, and where a guide comes close to a linked problem.

## The xUnit test patterns

The pages of [xunitpatterns.com](http://xunitpatterns.com/), the online draft of the patterns of G. Meszaros, *xUnit Test Patterns: Refactoring Test Code* (2007), copyright 2003-2008. Each page says the published book may differ and gives the book's page; that page is listed with each pattern. The site refuses HTTPS (the connection to port 443 is refused), so the pages were fetched over HTTP, and the guides link them with `http://`, as `batch-and-streaming` already links one source. Used in `what-a-test-checks`, `stubs-spies-mocks-and-fakes`, `deterministic-tests` and `test-suite-design`.

| # | Claim | Source |
|---|-------|--------|
| X1 | A test double replaces a depended-on component (DOC) that cannot or should not be used in the test; it need not behave exactly like the real DOC, only provide the same API so the SUT thinks it is the real one; the name comes from a film's stunt double | Quote: [*Test Double*](http://xunitpatterns.com/Test%20Double.html), book page 522 |
| X2 | A test stub gives the test a control point for the SUT's indirect inputs, which lets the test force the SUT down paths it might not otherwise execute | Quote: *Test Double*, "Variation: Test Stub"; [*Test Stub*](http://xunitpatterns.com/Test%20Stub.html), page 529 |
| X3 | A test spy is an observation point for indirect outputs: it captures the calls the SUT makes and saves them for later verification by the test; "just a" test stub with recording capability | Quote: *Test Double*, "Variation: Test Spy"; [*Test Spy*](http://xunitpatterns.com/Test%20Spy.html), page 538 |
| X4 | A mock object verifies the indirect outputs as the SUT exercises it; an unexpected call or wrong arguments fail the test immediately; a strict mock fails when expected calls arrive out of the specified order, a lenient one notes the call and carries on; missed calls are found by a final verification | Quote: [*Mock Object*](http://xunitpatterns.com/Mock%20Object.html), page 544, "Mock Objects can be either strict or lenient" and "Usage" |
| X5 | A fake object is a much simpler, lighter-weight implementation of the DOC, such as an in-memory database; the author encapsulated database access behind a persistence layer interface, replaced the database with in-memory hash tables, and made the tests run 50 times faster | Quote: [*Fake Object*](http://xunitpatterns.com/Fake%20Object.html), page 551; *Test Double*, "Variation: Fake Object" |
| X6 | A dummy object is passed when neither the test nor the SUT cares about it, and "isn't really a Test Double per se" | Quote: *Test Double*, "Variation: Dummy Object"; [*Dummy Object*](http://xunitpatterns.com/Dummy%20Object.html), page 728 |
| X7 | Excessive use of test doubles can cause fragile tests through overspecified software; at least one test should verify that the SUT works without a test double | Quote: *Test Double*, "When To Use It" |
| X8 | State verification inspects the SUT's state after it is exercised; behaviour verification captures the indirect outputs as they occur | Quote: [*State Verification*](http://xunitpatterns.com/State%20Verification.html), page 462; [*Behavior Verification*](http://xunitpatterns.com/Behavior%20Verification.html), page 468 |
| X9 | A four-phase test runs fixture setup, exercise SUT, result verification and fixture teardown in sequence; setup establishes the "before" picture; teardown puts the world back into the state in which you found it | Quote: [*Four-Phase Test*](http://xunitpatterns.com/Four%20Phase%20Test.html), page 358 |
| X10 | Assertion roulette: it is hard to tell which of several assertions within the same test caused a failure | Quote: [*Assertion Roulette*](http://xunitpatterns.com/Assertion%20Roulette.html), page 224 |
| X11 | Conditional test logic: a test contains code that may or may not be executed; test methods must be simple enough to not need tests | Quote: [*Conditional Test Logic*](http://xunitpatterns.com/Conditional%20Test%20Logic.html), page 200 |
| X12 | An erratic test sometimes passes and sometimes fails; causes include interacting tests, interacting test suites, lonely test (runs in a suite but not alone, depending on another test's fixture), resource leakage, resource optimism, unrepeatable test (behaves differently on the first run), test run war (failures when several people run tests against a shared resource such as a database) and nondeterministic test (different values on each run) | Quote: [*Erratic Test*](http://xunitpatterns.com/Erratic%20Test.html), page 228, the "Cause" sections |
| X13 | Overspecified software: a test says too much about how the software should be structured or behave, describing how it does something rather than what it should achieve; sensitive equality: objects are converted to strings and compared with an expected string; both are causes of fragile tests | Quote: [*Fragile Test*](http://xunitpatterns.com/Fragile%20Test.html), page 239 |

## Essays, articles and a lecture

Cited by title and date. The guides do not name the authors of the essays and articles; the addresses of four of them carry a person's name.

| # | Claim | Source |
|---|-------|--------|
| A1 | Arrange (set up the object, with collaborators that may be test objects), act (act on it), assert (make claims about it); writing the assert first, asking "Suppose it worked; how would I be able to tell?" | Quote: [*3A – Arrange, Act, Assert*, 26 April 2011](https://xp123.com/3a-arrange-act-assert/) |
| A2 | "program testing can be a very effective way to show the presence of bugs, but is hopelessly inadequate for showing their absence"; ACM Turing Lecture 1972 | Quote: [E. W. | A3 | The essay follows Meszaros's vocabulary: dummy, fake, stub, spy and mock; only mocks insist on behaviour verification, the other doubles can and usually do use state verification; the classical style uses real objects where possible and a double where the real thing is awkward; the mockist style always uses a mock for any object with interesting behaviour | Quote: [*Mocks Aren't Stubs*, 2 January 2007](https://martinfowler.com/articles/mocksArentStubs.html) |
| A4 | Many more low-level unit tests than high-level broad-stack tests through a GUI; GUI tests are brittle, expensive to write and time consuming to run; end-to-end tests are more prone to nondeterminism; the term ice-cream cone; the assumption that broad-stack tests are expensive, slow and brittle, and that lower-level tests are not needed if high-level ones are fast, reliable and cheap to modify; an intermediate layer through a service or API layer; high-level tests as a second line of defence, a failure meaning a missing or incorrect unit test, to be replicated with a unit test before the fix; end-to-end, UI and customer-facing tests are orthogonal characteristics; most people know the pyramid from a 2009 book, *Succeeding with Agile*, which calls it the "Test Automation Pyramid" | Quote: [*Test Pyramid*, 1 May 2012](https://martinfowler.com/bliki/TestPyramid.html), including its Etymology section |
| A5 | Contract tests check that all the calls against your test doubles return the same results as a call to the external service would; they run on the rhythm of changes to the external service, often once a day; a failure need not break the build but should trigger a task and a conversation; consumer-driven contracts let the supplier run copies of your contract tests; contract tests check the contract, not necessarily the exact data | Quote: [*Contract Test*, 12 January 2011](https://martinfowler.com/bliki/ContractTest.html) |
| A6 | Provider contracts are closed and complete, singular and authoritative; consumer contracts are open and incomplete, multiple and non-authoritative, expressing a subset of the provider's capabilities; consumer-driven contracts are closed and complete, singular and non-authoritative, derived from consumer expectations; expectations can be captured in a document at simplest, and, going a little further, as unit tests asserting each expectation with each build | Quote: [*Consumer-Driven Contracts: A Service Evolution Pattern*, 12 June 2006](https://martinfowler.com/articles/consumerDrivenContracts.html), sections *Provider Contracts* to *Implementation* |

The arrange-act-assert post (2011) says in its History section that the pattern was named in 2001; the guide gives no date for the name.

## Coverage and mutation testing

| # | Claim | Source |
|---|-------|--------|
| J1 | Mutants are faulty programs made by simple syntactic changes; a mutant whose result differs from the original's on some test is killed, otherwise it survives; equivalent mutants always produce the same output as the original; detecting all of them automatically is impossible because program equivalence is undecidable; the mutation score is killed mutants over non-equivalent mutants | Quote: Y. Jia and M. Harman, *An Analysis and Survey of the Development of Mutation Testing*, IEEE Transactions on Software Engineering 37(5), 2011, pages 649 to 678, [doi:10.1109/TSE.2010.62](https://doi.org/10.1109/TSE.2010.62), §I and §II.B; read from [a copy in a course's readings](https://web.eecs.umich.edu/~weimerw/2020-481F/readings/mutation-testing.pdf) |
| J2 | Mutation testing traces back to a 1971 student paper by Richard Lipton; the field's birth is in papers by DeMillo and others and by Hamlet in the late 1970s | Quote: Jia and Harman, §I |
| J3 | The competent programmer hypothesis and the coupling effect were introduced by DeMillo and others in 1978; the coupling effect: "Test data that distinguishes all programs differing from a correct one by only simple errors is so sensitive that it also implicitly distinguishes more complex errors"; test data developed to kill first-order mutants killed over 99% of second- and third-order mutants | Quote: Jia and Harman, §II.A |
| J4 | Mutant sampling, selective mutation, which leaves out the operators that generate the most mutants (2-selective: mean mutation score 99.99% with 24% fewer mutants), and weak mutation (a mutant is checked right after the mutated component executes) reduce the cost | Quote: Jia and Harman, §III.A and §III.B |
| U1 | 357 real faults in 5 open-source applications of 321,000 lines, 230,000 mutants; a coupling effect for 73% of real faults; 10% need a new or stronger operator, 17% are not coupled; mutant detection correlates with real fault detection, statistically significantly, independently of code coverage, and more strongly than statement coverage | Quote: R. Just, D. Jalali, L. Inozemtseva, M. D. Ernst, R. Holmes and G. Fraser, *Are Mutants a Valid Substitute for Real Faults in Software Testing?*, FSE 2014, pages 654 to 665, [doi:10.1145/2635868.2635929](https://doi.org/10.1145/2635868.2635929), abstract and §1; read from [an author copy](https://homes.cs.washington.edu/~rjust/publ/mutants_real_faults_fse_2014.pdf) |
| I1 | 31,000 test suites for five systems of up to 724,000 lines; statement, decision and modified condition coverage; effectiveness measured with mutation testing; low to moderate correlation once suite size is controlled; stronger coverage gives no more insight; coverage is useful for finding under-tested parts but should not be used as a quality target | Quote: L. Inozemtseva and R. Holmes, *Coverage Is Not Strongly Correlated with Test Suite Effectiveness*, ICSE 2014, pages 435 to 445, [doi:10.1145/2568225.2568271](https://doi.org/10.1145/2568225.2568271), abstract; read from [an author copy](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf) |
