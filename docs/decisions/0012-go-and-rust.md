# ADR 0012: Go and Rust are optional languages per problem, then required of every problem

| Field | Value |
|-------|-------|
| Status | Accepted |
| Date | 2026-10-29 |
| Spec | [problem-format](../specs/problem-format.md#type-mapping), [runners](../specs/runners.md#invocation) |

## Context

The catalog is practiced in Python, TypeScript, Java and Kotlin. Go and Rust are the next languages an interview asks for, and both differ from the existing four in ways that shape the design:

- Both compile ahead of time. There is no module to load: a missing function or a wrong signature is a compile error, which conformance fixture 9007 expects as a `load_error`.
- Neither has a reflection API that finds an unexported function by name. Go can call a function value through `reflect`; Rust cannot call anything it was not generated to call.
- "Every language" was spelled `tuple(Language)` in several defaults (`languages` of a problem, `cstudy next`, IDE actions, verify coverage). Adding enum members would have made every problem require Go and Rust references at once, and failed the ready check of all of them.
- The catalog has 218 problems with about 2.3 approaches each. Reference solutions in two more languages are about 1,000 files.

A spike (scratch code, not merged) built a Go runner and a Rust bridge for `two-sum` and an LRU cache, measured builds, and attached Delve and Xcode's `debugserver`. Warm rebuilds after an edit took 0.16 s in Go and 0.34 s in Rust (release profile), against 0.14 and 0.19 s for a trivial program.

## Decision

- **Optional per problem, then required.** `CORE_LANGUAGES` (Python, TypeScript, Java, Kotlin) is what a problem lists by default and what every default means. `OPTIONAL_LANGUAGES` (Go, Rust) are added to a problem's `languages` once its references exist. The schema requires the four core languages and allows `go` and `rust` on top; the concurrency and debugging tracks keep their subset rule. Ready, verify, `start` and `next` already work from the listed languages, so a problem that does not list Go is never offered, started or required in Go.
- **Full backfill, then a flip.** Go and Rust references are written for the whole catalog in batches by pattern, each batch passing the full verify gate. When the backfill reaches every problem, one final change makes all six languages required and `CORE_LANGUAGES` stops being a separate set. Recorded exceptions: `0055-linked-list-cycle` has no Rust reference unless a clean cyclic list representation exists, and the debugging track gets new Go- and Rust-native bug problems instead of ports (0240 to 0243 list only `go`, 0244 to 0247 only `rust`). The flip applies to the tracks that must list the core languages today; the concurrency and debugging tracks keep their subset rule, so their problems keep the languages they list.
- **Exhaustive language dispatch.** Every `match` on `Language` in layout, targets, buggy stubs, stub checks and the VS Code attach configuration ends in `assert_never`, and a test requires every `Language`-keyed table to hold a row per language, so a forgotten language is a type error or a failing test, never a silent fall-through to JVM paths.
- **Layout.** Go: `go/practice/<snake_slug>/<snake_slug>.go`, one package per problem, so a broken problem never blocks another. Rust: `rust/practice/<snake_slug>.rs`, a Cargo example built as a library crate. References are `solutions/<approach>.go` and `.rs`. A Go file name the go tool ignores (a stem ending in a GOOS, a GOARCH or `_test`, such as `sort_windows`) gets a `_code` suffix, so no slug or approach id makes a problem unrunnable ([Go file names](../specs/runners.md#go-file-names)).
- **Names.** Go is idiomatic: functions `twoSum`, constructors `NewLRUCache`, exported PascalCase methods (reflection only finds exported ones). Rust is snake_case for functions, methods and parameters, with `new` as the constructor. `member_name` takes the role of the name, and the request carries `names.constructor`. Reserved-word check S3 considers only the languages a problem lists.
- **Types.** Rust nodes follow LeetCode: `Option<Box<ListNode>>`, `Option<Rc<RefCell<TreeNode>>>`. Go `char` is `rune`. `decimal` is vendored shopspring/decimal in Go and rust_decimal in Rust, `date` is `time.Time` at UTC midnight and chrono `NaiveDate`; encoders are strict, as in [ADR 0011](0011-decimal-and-date-types.md). A Box list has no identity and cannot be cyclic, which costs exactly one problem.
- **Runners are standard library only.** The libraries for `decimal` and `date` are vendored, and builds run offline (`GOTOOLCHAIN=local`, `GOPROXY=off`, `cargo --offline`), so both languages work offline from the first run.
- **Runner architecture.**
  - Go compiles the user's package with a small generated registration file added through `go build -overlay`, so compiler errors and breakpoints name the real files. A reflective runner checks the types against the DSL and calls the target. Class kinds also get generated typed method thunks (see the amendments), since a reflective call per operation is slow enough to hide a cheap quadratic algorithm from the complexity ladder.
  - Rust has a bridge generated from the signature (decode, call, encode, and a `match` on the operation for classes) over a static runner library. The user's file and every reference enter as `#[path]` modules of a per-problem crate in a shared Cargo workspace and target directory.
  - A request names compiled code with `{"compiled": "user"}` or `{"compiled": "ref/<approach>"}`, since there is no path or class to load.
  - Compile diagnostics in the user's or a reference file mean a build failure (exit 2). Diagnostics only in generated code mean that target gets a `load_error`; the CLI rebuilds without it, at the cost of a second compile in the failure case only.
  - The Rust build uses the release profile with overflow checks and line tables for tests and benches, so `--perf` numbers are real and an `i32` overflow panics instead of wrapping.
- **Environment.** A missing Go or Rust toolchain is a `doctor` warning ("needed for `--lang go`"), not a failure. Debugging is VS Code only (Delve for Go; CodeLLDB with `debugserver` or `lldb-server` for Rust); IntelliJ gets tasks. Go and Rust run concurrent problems in the `threads` model, in a later step.
- **Budgets.** Warm `cstudy test` targets are 1 s for Go and 2 s for Rust. Full verify gets per-language budgets, and `cstudy verify --lang` gates a batch.

## Status

Complete. Every problem has Go and Rust references, and the flip made all six languages the default and the rule for the catalog: `ALL_LANGUAGES` is what a catalog problem lists unless it says otherwise and what every "all languages" default, coverage line and IDE action means, and check S13 requires every language that can express the problem. The schema only requires one language, since it cannot tell the catalog from a workspace. Unlike the plan, `CORE_LANGUAGES` stays, with a narrower meaning: the four languages whose toolchains every workspace needs, whose runners `cstudy doctor` handshakes and whose absence fails it. A missing Go or Rust toolchain still only warns, since only `--lang go` and `--lang rust` use it. `OPTIONAL_LANGUAGES` is gone.

The rule has four exceptions, each enforced by a check or by where the problem lives instead of left to the problem:

- **A language that cannot express the problem.** S13 keeps `rust` off a problem with cyclic list inputs or list identity (`0055-linked-list-cycle`, conformance fixtures 9006 and 9010) and requires every other language: a problem outside the concurrency and debugging tracks that leaves out a language S13 allows fails with `must list <language>`.
- **The concurrency and debugging tracks list any subset** (`LANGUAGE_SUBSET_TRACKS`), because a race or a bug often exists in some languages only. The Go-native bugs (0240 to 0243) list only `go` and the Rust-native ones (0244 to 0247) only `rust`; the original debugging problems (0206 to 0213) keep the languages their bugs exist in, the four core languages or fewer; concurrency problems leave out TypeScript where the race needs shared-memory threads, and `conformance-stress-async-determinism` (9018) stays Python and TypeScript.
- **An approach without a counterpart in a language.** A concurrency or debugging approach may name its own `languages`, a subset of the problem's; S7 rejects a reference outside them and the ready criteria require one in each, where every other approach needs a reference in every language of its problem. Four approaches use it, each explained in its language notes: `thread-safe-lru-cache`'s `locked-linked-map` (Java, Kotlin, Python: Go and Rust have no access-ordered map), `bounded-blocking-queue`'s `semaphores` (no TypeScript or Rust semaphore), `token-bucket-limiter`'s `cas-state` (Java, Kotlin) and `concurrency-limiter`'s `fair-semaphore` (Java, Kotlin, Go).
- **Problems you write yourself.** The six-language rule is the catalog's. A problem in a workspace's own `problems/` (`cstudy new` with the content bundled, ids from 5001) may list any non-empty subset, because the user has the toolchains they installed and no promise to anyone else. Without a `languages` line it lists the four core languages, what every problem listed before Go and Rust, so a problem written with `cstudy` 0.5.0 still verifies after an upgrade; making it six would have failed its `--require-ready` with `has no reference in go, rust`. The repository marks the layer (`ProblemMeta.workspace`) and S13 skips `must list` for it, while `cannot list` still applies. `cstudy new` writes `languages` explicitly, so the default never decides for a new problem, and says that the list can be trimmed.

`chess-move-validator`, the last problem without Rust, got it once the Rust stub and bridge wrote keyword names as raw identifiers (see the amendments).

The steps, in the order they landed: the `Language` members, `CORE_LANGUAGES` and `OPTIONAL_LANGUAGES`, the schemas, layout and naming, the per-language tables, and the "not set up yet" error (exit 4) for a listed language without an adapter. Go and Rust each: the stub generator, the runner for function, design and progressive problems in test and bench mode, the workspace's `go/` or `rust/` project, conformance fixtures 9001 to 9013 (Rust without 9006 and 9010, see below), and references for `two-sum`, `lru-cache` and `invert-binary-tree`. Both also run concurrent problems (the `threads` model, stress fixtures 9014 to 9017 and 9019). `cstudy doctor` checks `go`, `rustc` (1.80 or newer) and `cargo`, and warns about the Go and Rust files an older workspace lacks until `cstudy doctor --fix` writes them. The VS Code files recommend the Go and rust-analyzer extensions and set `GOTOOLCHAIN=local` and the rust-analyzer project, check and `--keep-going` settings; the tasks were already language-agnostic. `cstudy test --debug` starts the Go runner, built without optimizations, under a headless Delve (tested with 1.27.2), and the Rust runner, built with the dev profile, under `debugserver` (macOS) or `lldb-server gdbserver` (Linux, not yet tried on a Linux machine); VS Code attaches with the Go extension and with CodeLLDB, and `cstudy doctor` warns when Delve or the debug server is missing. Both support `decimal` and `date` with vendored libraries, shopspring/decimal in Go and rust_decimal and chrono in Rust (conformance fixtures 9020 and 9021). The references for the rest of the catalog followed in batches by pattern, and the flip above closed the plan.

## Amendments

Settled while building the Go runner (2026-10-29):

- **Go 1.24 or newer.** The build parses `go build -json`, which Go 1.24 introduced. The workspace's `go/go.mod` and the generated build module say `go 1.24`; the runner module itself needs only Go 1.22.
- **Package clause.** Reference and buggy files declare `package <snake_slug>`, the stub's own clause, and are copied unchanged, so a file moves between `solutions/` and the practice directory as is. Unlike the JVM, nothing is rewritten: Go does not require a package's name to match its directory, each approach still gets a package of its own, and the generated registration repeats whatever clause the file declares.
- **Support types live in the runner module.** `cstudy/support` is part of the runner module `cstudy`, which the workspace's `go.mod` replaces with `../.cs/runtime/runners/go`. A copy in the workspace module would give the runner and the solution two different `ListNode` types.
- **A missing symbol keeps the compiler's reason.** The second build passes the failing registrations' messages to the runner, so the `load_error` says why, for example `undefined: twoSum` or `cannot use generic function twoSum without instantiation`.
- **Concurrent `cstudy` processes.** The build holds an exclusive lock, and every run launches its own copy of the binary, removed when the run ends, so a build in one process never replaces the file another is about to start.
- **Per-language conformance.** The `decimal` and `date` round trips moved out of `conformance-types` into `conformance-decimal-date-types` (9021). A fixture runs in the languages its `meta.yaml` lists, so Go lists the fixtures it supports and needs no skip list in `expectations.json`.
- **The user's Go settings stay out of builds.** The go command reads an empty `GOFLAGS` as unset and falls back to the file `go env -w` writes, where `GOFLAGS=-mod=mod` failed every build in workspace mode. Builds run with `GOENV=off` and `GOFLAGS=-mod=readonly`, without the user's `GOOS`, `GOARCH` and `GOWORK`.

Settled while building the Rust runner (2026-10-29):

- **One harness package per problem and scope.** `.cs/build/rust` holds `test/`, `verify/` and `bench/` packages named `<scope>_<snake_slug>`, like Go's binaries per scope, so a broken reference never blocks `cstudy test` and the user's file never blocks `verify`. The workspace lists its members one by one: Cargo reads a glob that matches nothing as a path.
- **Edition 2021, Rust 1.80 or newer.** LeetCode's edition; the user's file compiles as a module of the harness crate, so the harness's edition is the user's. `rust/Cargo.toml` needs a target before the first problem starts, so it has an empty `lib.rs`.
- **Errors in the user's terms.** The bridge's module `user` is the file's name in a `load_error`, rustc's similar-name hint is kept, a private function says to declare it `pub`, and for a type mismatch the message says which side is the user's: rustc's "expected" is the user's parameter type for an argument, but the declared type for the result.
- **Identity is a node's address.** `no_alias_with` works on lists too: the call runs with freed memory retained (the runner's allocator skips frees during it), so a new node can never take the address of an input node the function dropped. `ref_of` and `as: index` on a list cannot work, since they need a second reference to a node a `Box` owns, and neither can a cyclic list input. Static check S13 keeps `rust` out of such problems: `0055-linked-list-cycle` and conformance fixtures 9006 and 9010.
- **Memory is `heap_peak`, high confidence.** A counting global allocator in `cs_runner` counts the case thread's allocations during the separate memory call only, from zero at its start; elsewhere an allocation pays one thread-local read.
- **The user's Cargo setup stays out of builds.** Builds run with empty `CARGO_ENCODED_RUSTFLAGS`, `RUSTC_WRAPPER` and `RUSTC_WORKSPACE_WRAPPER`, `--target <host>` and the release profile repeated as `--config`, without the user's `RUSTFLAGS`, `CARGO_TARGET_DIR`, `CARGO_BUILD_*` and `CARGO_PROFILE_*`, so a configured wrapper, rustflags, target or profile cannot break a build or change its semantics.
- **Panics.** A panic's `error.type` is `panic` (Rust panics have no type). The trace keeps the backtrace frames in the target's file, and the panic's location (indexing, overflow and `unwrap` report the user's line) stands in for an innermost function the release build inlined without a location.
- **Graph neighbors.** `GraphNode.neighbors` is `Vec<Rc<RefCell<GraphNode>>>`: a null neighbor is invalid, so the elements are not `Option`s.

Settled while adding concurrent problems (2026-10-29):

- **One model, one variant.** Go and Rust run the `threads` model only, with the variant `thread`: Go has no async runtime to choose, and Rust's would need tokio. `conformance-stress-async-determinism` (9018) stays Python and TypeScript.
- **Blocking methods look like any other.** Java marks a `blocking` method with `throws InterruptedException` because the JVM interrupts workers; Go and Rust have no interrupt, so their stubs declare such a method like Kotlin's, plainly, and the call blocks its goroutine or thread.
- **Goroutines and threads cannot be stopped.** After a failure or a stall the workers stop at their next op boundary; one blocked or spinning in user code is left running, and the runner asks for a restart (`restart_requested`, exit 3) when one still runs 200 ms after the run, as Python threads do. `conformance-stress-leak` (9019) therefore applies to Go and Rust.
- **Go broken references race on single-word fields only.** A data race on an `int`, a `bool` or a pointer stays memory-safe, but the Go runtime turns a concurrent map write into a fatal error that ends the runner process (a crash, which uses up one of the three crash restarts, instead of one failed run), and a slice, string or interface header torn between two goroutines can corrupt memory. Where the bug involves a map or a growing slice, the Go broken reference uses `sync.Map`, atomics or a fixed buffer instead. The race detector (`-race`) is not used; it would flag unsynchronized access deterministically and is a possible follow-up.
- **A Rust concurrent class is `Send + Sync`, checked by the compiler.** The bridge registers `Entry::Concurrent` with `&self` methods, and its constructor passes the instance to `cs_runner::shared`, whose `Send + Sync` bound turns a `RefCell` or `Rc` field into a `load_error` in the user's terms, such as `` `RefCell<VecDeque<i32>>` cannot be shared between threads safely ``. Decoded calls move to the worker threads, so they must be `Send` too: a concurrent problem with node types (`Rc`) is `UnsupportedType` in Rust; none exists.
- **Rust broken references are logic races.** Safe Rust has no data race, so each one breaks atomicity or a wait instead: a check and an act under two separate lock acquisitions, `if` instead of `while` around `Condvar::wait`, a lock-order deadlock, or a relaxed atomic load followed by a separate store. A bug that safe Rust cannot express at all, an unguarded linked list or a list relinked under a read guard, leaves `rust` out of that broken reference's `languages`, and Rust gets one of its own (`thread-safe-lru-cache`: `split-locks`).
- **Broken references lose updates where the JVM's do.** A broken reference whose only failure is a window of a few instructions, a check and an increment on lossless atomics, was caught in only 7 or 8 of 10 runs while `cstudy verify` ran the JVM, Python and TypeScript runners in parallel. Like the JVM's `volatile` counter, the Go and Rust versions of `read-write-lock`'s `unlocked-count` lose increments (a plain field, a separate atomic load and store), which makes the count drift and fails nearly every run.

Settled while adding `decimal` and `date` (2026-10-29):

- **Go pins shopspring/decimal v1.5.0.** The newest release, v1.6.0, was eleven days old; v1.5.0 already has the correctly rounded `Pow` and the `MaxDecodeExponent` guard. The module is copied, without its tests, into `runners/go/third_party/` and reached through `replace` in the runner module, the workspace's `go/go.mod` and the build's `go.work`, so neither a build nor the editor needs the network. A `vendor/` directory would not do: Go reads one only in the main module, and the build's main modules are the generated `csbuild` and the user's `workspace`.
- **Canonical decimals do not use `String`.** Since v1.5.0, `String` follows the package settings `TrimTrailingZeros` and `UseScientificNotation`, so the Go encoder writes the coefficient and exponent itself. The package's settings are global variables, and every case starts with their defaults, as every Python case starts with a fresh decimal context: a reference that sets `DivisionPrecision` cannot change the user's results in the same bench process. The library has no `HALF_DOWN`; [problem-format](../specs/problem-format.md#decimal-and-date) shows how to write it.
- **A Go `date` is a UTC midnight, strictly.** The encoder rejects a `time.Time` in another location, even one at offset zero, a time of day, and years outside 0001 to 9999, so a solution that builds its result with `time.Local` fails on every machine, not only outside UTC.
- **Rust pins rust_decimal 1.43.0 and chrono 0.4.45, without default features.** `cargo vendor` copies them and their three dependencies (`arrayvec`, `num-traits`, `autocfg`) into `runners/rust/vendor`, without tests, benches and examples, and every build passes the source replacement as `--config`, since `cstudy` keeps the user's Cargo configuration out of its builds. rust_decimal gets `maths` (`powu`, `sqrt`, as Go's `Pow` and Java's `pow`) but not `std`: its weak `dep?/std` features would put 48 optional crates in `Cargo.lock`, and `cargo vendor` copies whatever the lock lists. chrono gets `std` and not `clock`, so no time zone crates and no `Utc::now`. The trimmed copies take 2.3 MB.
- **The harness depends on both crates directly.** A solution is a module of the harness crate, and `use rust_decimal::Decimal;` resolves only through the crate's own dependencies, so every harness package declares them as `cs_runner` does, and the workspace's `rust/Cargo.toml` lists them as dev-dependencies with a `rust/.cargo/config.toml` for rust-analyzer.
- **rust_decimal is narrower than the DSL.** It holds at most 28 digits after the point and a magnitude below 2^96, while the DSL allows 28 significant digits at any scale, so `0.00000000000000000000000000001` is a valid `decimal` that a Rust case rejects as `InvalidInput`. The decimals in the catalog's test files stay far inside both, with at most 14 digits after the point.

Settled while backfilling the catalog (2026-10-29):

- **Methods are called through generated thunks.** A reflective `Call` costs about 120 to 250 ns and four allocations per operation, inside the timed region of a bench. The complexity check tolerates only a constant per call, so on a design problem with a cheap quadratic reference (0013's linear list scan: slope about 1.4, time / n^2 varying 5 to 8 times against a 4x tolerance) the constant buried the growth and the ladder failed. Rust never had the problem: its bridge is generated, so the call is direct. Go now generates a second file per class package, `zz_cs_thunks.go`, with one function per method that asserts the arguments to the declared Go types and returns the result as an `any` (about 10 to 20 ns). The runner keeps reflection for what it does well, checking signatures and producing the friendly `SignatureMismatch`, and calls a thunk only after that check passes and only when the constructor returns the type the thunks were written for. The file is separate from the registration so that the second build can leave out just the thunks when a method's parameters differ from the signature, and reflection reports it as before. Rejected: resolving each method once (`Method(i)` per call is not the cost, `Call` is), leaving dispatch out of the timing (the timer's own tick is about 42 ns and noise), subtracting a hash-set baseline (the baseline is as noisy as the signal), and per-problem sizes or tolerances (they hide the symptom). Concurrent classes and functions keep reflection: stress workers need it, and a function is called once per input. The thunk file's name is excluded from traces so a panic names the user's lines only.
- **Declared classes follow the libraries.** `last-stone-weight`'s `sort-each-round` re-sorts a list that is sorted but for the stone just appended. Every library sort the references use detects that order (Timsort, Java's run merging, Rust's driftsort, Go's pdqsort through its partial insertion sort), so the approach is O(n^2), not the O(n^2 log n) of a generic sort; Python measured it in the n^2 band too, and only Rust, whose sort is about 0.4 ns per element, drifted past the tolerance (4.4x to 7.8x against n^2 log n). The declaration changed for every language rather than per language: the format has one `time_class` per approach, and no language here sorts that list in O(n log n).
- **Lower-order terms set the smallest size, not the class.** Against n^2 the same Rust reference still drifted 3.4x to 4.9x over 100 to 10^4 stones under load: a round costs about 100 ns before it sorts anything, an O(n) term over the game that a fixed per-call cost cannot stand for. Starting the ladder at 300 brought the drift to 2.4x to 2.6x (Go 1.7x, Java 1.6x) over 1.5 decades; artificially slower references and per-language declarations were rejected.
- **Searches that stop early need inputs without early exits.** `word-search` timed one random board per size; the board drawn, not the word length, set the time (2 to 113 µs in Python at the largest size across seeds, and the size of 10 was often cheaper than 5), Go and Rust took under a microsecond per call, and their band flipped between runs while Python passed on one heavier input. A generator family that every approach must search to the end at the ladder sizes (a parity trap: the word's end letters sit on the cell color that a walk of its length cannot reach from the first start) made the slope 4.6 to 5.4 in all six languages. Larger sizes were not possible (the constraints cap the word at 15 and the board at 6 by 6), and a ladder exemption for fast calls would have hidden that the Python pass was luck too.
- **Stress runs measure one runner at a time.** With three or four agents loading 11 cores, `cstudy verify` of `token-bucket-limiter` and `read-write-lock` failed 4 of 6 times while every language's runner ran at once: Kotlin, Rust and Python broken references were caught 7 or 8 times in 10, and a correct Rust run used 31% of its deadline. The languages still build side by side, but their runners take turns; 5 of 6 verifies then passed at the same load, the slowest correct run at most 13% of its deadline. The 9-of-10 rule and the 25% margin stay: relaxed under load, they would pass cases that miss races on an idle machine, where users run. A failure on a busy machine instead adds a warning naming the load. Python's `unlocked-count` was still caught only 8 times in 10 once at load 13, and 10 of 10 in six runs at load 6, so its stress case stays as it is.
- **Rust keywords are raw identifiers.** `chess-move-validator` has a method `move`, a Rust keyword, and S3 kept Rust out of it. Rust spells any keyword but `self`, `Self`, `super` and `crate` as a raw identifier, so the stub declares `pub fn r#move(&mut self, ...)` and the bridge calls `instance.r#move(...)`, while the operation, the request's `names` and every message keep `move` (a `load_error` drops the `r#` rustc writes). S3 rejects only the four keywords that have no raw form. Renaming the method for every language, or for Rust alone, was rejected: the name is the problem's, and a raw identifier is what a Rust programmer writes for it.
- **JVM runs copy the runtime's jars.** Both Gradle projects include the runtime's runner build, so the first builds after a runner change rebuilt `runner.jar` in place, Java and Kotlin at once, while another JVM could be reading it (`NoClassDefFoundError: BadRequestException` before `hello`). Builds now hold a runtime lock, shared while the runtime's sources and jars match the last exclusive build and exclusive otherwise, and every run loads private copies of the jars, as it already did of the class directories.

## Consequences

- Existing problems, stubs and requests are unchanged: the four core languages produce byte-identical output. During the backfill every default that meant "all languages" meant the core four; since the flip it means all six.
- During the backfill, `cstudy list --lang go` and `cstudy next --lang go` show only the problems that have Go references, and verify coverage lines show Go and Rust once a problem lists them.
- A language that is known but has no adapter fails with `rust stub generator is not set up yet` (exit 4) wherever an adapter is needed, and with "not available in rust" (exit 3) for a problem that does not list it. `cstudy doctor` only warns about a missing or old Go or Rust, never fails, and does not run their runners.
- Full verify grows: Go adds roughly 0.5 to 1.5 s per problem and Rust 1.5 to 4 s, and Cargo's target-directory lock serializes parallel Rust builds. The oracle and ladder checks cost more per added language.
- Go and Rust references written by agents need review at about twice the current reference volume.
- A cyclic linked list cannot be expressed in Rust with `Box`, so cyclic-list and list `ref_of` problems are Go-only (S13); `no_alias_with` on a list works in Rust.

## Alternatives considered

| Alternative | Why rejected |
|-------------|--------------|
| Require Go and Rust of every problem at once | Blocks the runners behind about 1,000 reference files, fails the ready check of all 218 problems, and doubles the verify cost before anything ships |
| Optional with no backfill plan | `cstudy next --lang go` would offer nothing until someone happened to write references |
| Port the debugging track | Its bugs are language specific (integer overflow and boxed equality are JVM-only, a mutable default argument is Python-only); Go and Rust get bugs of their own |
| Go `package` copy instead of `-overlay` | Compiler errors name the copy and Delve cannot set a breakpoint at the user's path |
| serde or a JSON crate in the Rust runner | About eight vendored crates, proc macros included, for a few hundred lines of codec |
| `byte` for Go `char` | Wrong for non-ASCII; `rune` is exact for the BMP the DSL allows |
| Persistent compile servers | The measured warm rebuilds already meet the budgets, and a daemon is state to keep correct |
